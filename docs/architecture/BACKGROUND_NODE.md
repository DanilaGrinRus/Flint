# Фоновая нода: дизайн и гейты

Статус: **только дизайн; реализация не начата.** Это не обещание и не разрешение
на изменение текущего поведения. В 0.1.69 нода живёт внутри процесса UI и
останавливается вместе с ним.

## Зачем

Сейчас `NodeManager` запускает официальный `grin.exe` как дочерний процесс UI.
Закрытие окна останавливает ноду, поэтому синхронизация прерывается, а следующий
старт снова догоняет цепь. Фоновая нода должна переживать закрытие окна,
перезагрузку и короткие потери сети, не превращаясь в скрытый процесс без контроля.

## Границы

Входит:

- один экземпляр ноды на профиль/сеть;
- запуск по явному согласию пользователя (автозапуск — отдельная опция);
- остановка из UI, корректное завершение по логаут/выключение;
- восстановление после падения ноды без потери chain data;
- видимый статус: высота, пиры, синхронизация, диск.

Не входит:

- собственная реализация консенсуса или ноды;
- удалённая нода/публичный сервис;
- майнинг;
- доступ к seed/паролю кошелька (нода не должна их видеть);
- мобильная версия (отдельный трек).

## Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Нода в процессе UI (сейчас) | просто, один lifecycle | закрытие UI останавливает синк |
| B. Отдельный supervisor + официальный `grin.exe` | изоляция падений, переживает UI | нужен второй компонент, autostart, IPC |
| C. Нода в потоке UI | нет второго процесса | падение ноды/паника убивает UI |

Выбран **B**: маленький supervisor (позже — отдельный бинарь) владеет процессом
`grin.exe`, хранит его PID/порт/секрет, перезапускает с backoff и отдаёт статус
через обычный node API. UI и кошелёк остаются клиентами и не владеют нодой.

## Контракт

- Один профиль данных = один supervisor и один `grin.exe`; второй экземпляр
  обязан отказаться, а не делить chain DB.
- Supervisor пишет PID-файл и состояние (`starting/syncing/ready/stopped/failed`)
  атомарно; UI читает его только как подсказку, истина — node API.
- Owner API остаётся только на loopback с Basic-auth; секрет — owner-only ACL,
  как сейчас. Foreign API не выставляется шире текущего.
- Остановка: Ctrl-Break/graceful, ожидание `Shutdown complete`, затем kill как
  fallback. Повторный запуск после жёсткого kill должен открывать ту же цепь.
- Autostart — opt-in, с записью в реестр/планировщик только по действию
  пользователя и с кнопкой удаления.
- Логи с ротацией и пределом размера; секреты в логи не попадают.

## Отказные сценарии

- падение `grin.exe`: backoff, счётчик попыток, видимая ошибка, без бесконечного
  рестарта;
- занятый порт/чужой процесс: fail-closed, не подключаться к неизвестной ноде;
- повреждённая/неполная chain data: нода не считается ready; UI не показывает
  нулевой баланс как факт;
- диск заполнен: предупреждение и остановка синка до освобождения места;
- logout/reboot: корректная остановка или восстановление после старта;
- удаление профиля: supervisor останавливает ноду и не оставляет сирот.

## Гейты до реализации

1. Отдельный ADR с выбором supervisor/autostart и моделью угроз.
2. Тесты: один экземпляр, второй отклонён; закрытие UI не убивает ноду; reopen
   переподключается; падение ноды перезапускается; graceful stop; logout;
   disk-full; повреждённая chain data; удаление профиля.
3. Ручная проверка на чистой Windows: autostart, отмена autostart, отсутствие
   сирот после выхода, обновление бинаря ноды.
4. Измерения: RAM/CPU/диск за сутки, поведение при спящем режиме и смене сети.
5. Отдельное решение владельца: включать ли фон по умолчанию (предлагается
   выключено).

## Открытые вопросы

- Отдельный бинарь supervisor или режим `flint-slint --node-supervisor`?
- Где хранить состояние supervisor: рядом с `data` или в `%LOCALAPPDATA%`?
- Как обновлять `grin.exe`, пока supervisor работает?
- Нужен ли отдельный tray-агент или достаточно автозапуска supervisor?
- Как поступать с несколькими профилями: один supervisor на профиль или общий
  с мультиплексированием?

До ответов на эти вопросы код фоновой ноды не добавляется; текущий `NodeManager`
остаётся единственным путём запуска.

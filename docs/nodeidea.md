# nodeidea — фоновая нода и быстрый первый запуск

Статус: **предложение**. Не входит в текущий план стабилизации
(`docs/PLAN.md`); в `docs/status/ROADMAP.md` фоновая нода — этап
после фазы 5. Основание: `docs/architecture/NODE_ARCHITECTURE.md` (весь
§«Что потребуется» оттуда, здесь — конкретика реализации). Документ не
меняет код; каждая фаза — отдельной задачей со своим гейтом.

## 1. Постановка

Сейчас нода живёт, только пока открыт Flint: `auto_start_node` поднимает
`grin.exe` дочерним процессом, при выходе — остановка
(`NodeManager::Drop`). Повторный запуск = повторная догонка.

Факты о стоимости синхронизации (см. обсуждение 2026-10-27):

- первая синхронизация testnet-ноды: ~1–1.5 ч, основное время — фаза
  заголовков; скачивание состояния — минуты, верификация kernels/
  rangeproofs — CPU-bound и неизбежна;
- инкрементальная догонка (блоки за ~48 ч): минуты;
- локальные объёмы (`.node/testnet`, 5.8 ГБ): `txhashset` 2.9 ГБ,
  `multi_lmdb` 2.6 ГБ, `header` 370 МБ.

Вывод: повторная синхронизация при каждом запуске — главная боль;
первичная — второстепенная. Поэтому два **независимых** средства:

1. **Фоновая нода** (§2–§7) — устраняет повторную длительную догонку.
2. **Bootstrap-снапшот** (§8) — устраняет долгий первый запуск; общий
   формат с мобильным направлением (§9).

## 2. Механизм фона: scheduled task vs Windows Service

| Критерий | Scheduled task (at logon) | Windows Service (SYSTEM) |
|---|---|---|
| Права | пользователь — те же пути/ACL секретов | SYSTEM — перенос секретов, ACL, сеть |
| Код | нет инсталлятора службы, нет elevated-путей | service control manager, recovery API |
| Сеть/Tor | пользовательская сессия, прокси как сейчас | отдельный профиль, координация с мессенджером |
| Поверхность атаки | минимальная | выше (служба слушает/стоит всегда) |
| Перезапуск при падении | настройки задачи (N попыток, задержка) | service recovery, надёжнее |
| Автозапуск без логона | нет | да (серверный сценарий) |

Рекомендация: **scheduled task at logon под пользователем**. Сервис —
опционально позже для серверного сценария, не блокирует этапы.

## 3. Компоненты

1. **`NodeLauncher`** (рефакторинг `crates/core/src/node.rs`): выделить
   из `NodeManager` конфиг-генерацию, `ensure_api_secrets`,
   `wait_for_api`, `log_tail`, health-check. Общий код UI и супервизора.
   Поведение UI не меняется — весь текущий suite `node.rs` зелёный.
2. **`flint-noded`** — новый маленький бинарь (отдельный crate в
   workspace, без UI-зависимостей): запуск `grin.exe` через `NodeLauncher`,
   watchdog, ротация лога, статус-эндпоинт, graceful stop.
3. **`tools/install-node-task.ps1`** — идемпотентная установка/удаление
   задачи `schtasks` (проверка существующей задачи перед созданием).
4. **UI** (`crates/slint-ui`): настройка «нода в фоне», карточка статуса,
   кнопки старт/стоп.

## 4. Модель владения нодой

- Нода, поднятая UI-процессом: владелец — этот процесс; гасится на выходе
  (как сейчас).
- Нода, поднятая `flint-noded`: владелец — супервизор. UI **только
  attach-ится** через существующие проверки (порт отвечает, секрет совпал,
  `chain`/`user_agent` совпали — см. `identity_matches`).
- `NodeManager::Drop` гасит только собственный child; проверка «порт
  занят чужим сервисом → ошибка» сохраняется.
- Смена сети (testnet↔mainnet): задача пересоздаётся с другими аргументами
  (каталог, порты); старая нода остановлена до пересоздания. Mainnet не
  стартует молча — действует существующий mainnet-гейт.

## 5. Фазы

**Фаза 1 — NodeLauncher.** Рефакторинг без смены поведения. Гейт: весь
suite `node.rs` + selftest зелёные; diff — только перенос кода.

**Фаза 2 — `flint-noded`.** Запуск ноды; watchdog:

- процесс завершился → рестарт с backoff (1, 2, 4… максимум 15 мин);
- зависание: tip/`sync_status` и лог не меняются N минут → мягкий
  рестарт (SIGTERM-аналог → kill), счётчик подряд → пауза 30 мин и запись
  в статус;
- лог-ротация `node.log` (текущий код читает tail целиком);
- статус-эндпоинт на loopback со своим секретом: фаза, высота, peers,
  возраст tip;
- graceful stop: HTTP `/stop` (секрет) + завершение по сигналу.

Гейт: kill-дрилл (убить `grin.exe` — супервизор поднимает; убить
`flint-noded` — задача перезапускает), утечек в логах секретов нет.

**Фаза 3 — установка задачи.** `schtasks` at logon, restart-on-failure
(3 попытки с задержкой 1 мин), условие «только при наличии сети»
(опция). Удаление — отдельной командой. Гейт: повторная установка
идемпотентна; после перезагрузки нода поднялась сама.

**Фаза 4 — UI.** Настройка «нода в фоне» (установить/удалить задачу,
показать команду), карточка «нода работает в фоне, высота N», стоп/старт
(стоп = остановить задачу и процесс). Две копии Flint: обе attach-ятся,
ни одна не убивает чужую ноду. Гейт: ручной сценарий двух копий +
kill/restart.

**Фаза 5 — безопасность и обновления.** ACL на секреты ноды (`win_acl`,
требования SENT-02/SENT-01 из `docs/PLAN.md` применяются и сюда);
foreign API — только loopback/через прокси (как сейчас); автоматическое
обновление `grin.exe` по механизму `tools/fetch-node.ps1` (SHA256 +
подпись релиза), остановка→замена→старт→проверка непрерывности высоты.

## 6. Гейты (приёмка всего этапа)

1. UI закрыт ≥1 ч → нода синхронизируется, высота растёт.
2. `grin.exe` убит → супервизор поднимает, UI при старте attach-ится.
3. Обрыв питания → после логона задача стартует, нода догоняет.
4. Две копии приложения — одна нода.
5. Смена testnet↔mainnet — старая нода остановлена, новая поднята.
6. Обновление бинаря ноды — без ручных действий, высота непрерывна.
7. Ни один секрет ноды не попал в логи/статус-эндпоинт.

## 7. Риски и открытые вопросы

- **Tor.** Мессенджер поднимает свой Tor с жизненным циклом UI. Фоновая
  нода для синхронизации Tor не нужна; связь нода↔мессенджер не требует
  onion-адресов. Решение: фоновая нода — без Tor; Tor живёт в UI-процессе
  как сейчас. Открытый вопрос: slatepack-отправка при закрытом UI —
  отложена до отдельной задачи (реле/gateway).
- **Сон/гибернация.** После резюме нода догоняет сама; специальной
  логики нет.
- **Диск.** `grin` квот не поддерживает: только мониторинг каталога и
  предупреждение в UI при превышении порога (значение — в настройках).
- **Батарея.** Условие задачи «только от сети» — по умолчанию выключено,
  опция в настройках.
- **mainnet.** Все гейты §6 сначала на testnet; mainnet — после
  выполнения `docs/status/MAINNET_READINESS.md`.

## 8. Bootstrap-снапшот (общий для десктопа и мобильного)

Цель: первый запуск на новом устройстве — минуты вместо часов.

- **Что поставляем:** каталог данных ноды на высоте H (headers +
  txhashset + lmdb) + подписанный манифест (высота, хеши корней MMR,
  версия ноды). Поставка: с релизом (testnet) или загрузка при первом
  запуске (mainnet).
- **Верификация:** заголовки до H — локальная проверка PoW; состояние —
  по корням MMR из заголовков (включая повторную выборку состояния через
  PIBD: тогда доверие сводится к hashpower-большинству, а не к
  производителю снапшота).
- **Модель доверия:** эмиссия и спенды до H не перепроверяются из полной
  истории (её нет). Для testnet — по умолчанию; для mainnet — opt-in с
  явным текстом в UI, полный sync остаётся доступным.
- **Реализация:** точка входа — предзаполненный `node_dir` перед первым
  стартом; дальше штатная инкрементальная синхронизация. Гейт: нода со
  снапшотом и нода с полным sync сходятся в одном tip и одном MMR-root.

## 9. Связь с мобильным направлением (iOS)

Кратко (подробный план — отдельным документом):

- кошелёк: embedded-бэкенд (`docs/architecture/BACKENDS.md`) портировать
  в Swift через FFI; нода по умолчанию — удалённая (своя VPS/desktop
  или публичная через Tor);
- встроенная pruned-нода на устройстве возможна только «пока приложение
  открыто» (фоновые лимиты iOS) и **только с bootstrap-снапшотом §8** —
  формат общий, работа не дублируется;
- входящие: slatepack-first через мессенджер (уже в workspace) —
  обнаружение платежа не зависит от скана ноды; скан — периодическая
  сверка.

Мобильный план не начинается до закрытия фазы 1–2 фоновой ноды:
`NodeLauncher` — тот же код, который потребуется встроенной ноде на
iOS.

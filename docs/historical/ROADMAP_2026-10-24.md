# Flint: дорожная карта (ред. 3, 2026-10-24)

> **HISTORICAL:** сохранённый срез, не текущий план. Актуальная дорожная карта —
> [../status/ROADMAP.md](../status/ROADMAP.md).

> **Tauri удалён 2026-10-26; актуальная оболочка — Slint.** Исторические
> упоминания Tauri/WebView2 ниже сохранены как журнал решения.

> Текущий счёт закрытия — [KRead.md](../KRead.md), внешние приёмки —
> [PSWork.md](../PSWork.md); этот файл описывает фазы и сохранённые срезы.

План приёмки, а не обещание релиза. Ревизия 2 изменила порядок фаз из внешнего
`ROADMAP_TO_MATURE.md`: durability и защита оболочки идут раньше миграции seed.
Ревизия 3 добавляет фазу 0.5: при разборе исходников `grin 5.5.2` выяснилось,
что owner/foreign API ноды по умолчанию стартует без аутентификации. Это дыра
в текущих сборках, а не будущая функция, поэтому она идёт до фазы 1.
Обоснование — в конце документа.

## Принципы

1. **Гейт — это сценарий, а не счётчик.** «Все тесты зелёные» не значит ничего:
   десятки тестов зелены и при полностью дырявом коде (см. [STATUS.md](../status/STATUS.md)).
   Фаза закрыта, когда пройден описанный сценарий на живой цепи, и его можно
   повторить.
2. **Никаких заявлений о готовности по скриншотам, demo-бэкенду или компиляции.**
3. **Одна фаза — один набор изменений с тестами.** Статус в STATUS.md обновляется
   в том же изменении, а не отдельным «отчётом о прогрессе».
4. **Ошибка в пользу отказа.** Всё, что может создать впечатление успеха
   (баланс, «получено», «синхронизировано»), по умолчанию показывает
   неопределённость, а не оптимистичный вариант.
5. **Testnet по умолчанию и всегда.** Mainnet — только после фазы 6 и только
   вручную.

### Инфраструктура, без которой гейты недостижимы

Тестовая цепь Grin — миллионы блоков; полная синхронизация занимает часы и
гигабайты. Поэтому нужен **один долгоживущий узел** (отдельная машина или
CI-агент) с готовой `chain_data`, к которому подключаются тесты, плюс снапшот
каталога данных для крэш-тестов. Это требование к окружению, а не пункт плана:
без него фазы 2–4 будут вечно «в процессе».

## Фаза 0 — честность и деньги (P0) — сделано 2026-10-23

Цель: приложение перестаёт врать и перестаёт терять доступ к средствам.

**Статус: закрыта по коду и автотестам.** Что именно сделано и чем проверено —
[docs/status/STATUS.md §3](../status/STATUS.md#3-исправлено-в-фазе-0). Единственное, что осталось
от гейта, — прогон отмены на живой ноде; он переведён в фазу 1 вместе с
крэш-тестами, потому что требует того же стенда.

- Отмена через `Owner::cancel_tx(None, None, Some(uuid))`, удаление записи — только
  после успеха; для входящих отмена запрещена (контрагент мог опубликовать).
- Валидация `slate_id` как канонического UUID; отказ на `/`, `..`, суффиксы — до
  любого доступа к файлу.
- Атомарная запись pending: временный файл → `write_all` → `sync_all` → `rename`.
- Pending сохраняется **до** `tx_lock_outputs`; при ошибке блокировки — попытка
  отмены и удаление записи.
- Адрес получателя: невалидный = ошибка; plaintext только при явном `manual`
  с предупреждением в UI.
- `synced = false` до появления настоящего статуса (фаза 2); UI не показывает
  зелёный индикатор по факту ответа RPC.
- `--selftest`: собственный каталог с маркером и `uuid`, `FLINT_DATA_DIR` не
  используется как цель; удаляется только созданный каталог.
- CSP: строгая политика (`default-src 'self'`), окно с `on_navigation` — наружу
  не уходит. `withGlobalTauri` остаётся: UI использует `window.__TAURI__`.
  В 0.1.51 добавлены capability `main` (`core:default`) и `freezePrototype`;
  собственные команды в Tauri 2 capability-файлом не ограничиваются — остаются
  CSP, одно окно и отсутствие удалённого контента.
- demo-reset скрыт вне браузерного demo-режима.

**Гейт:** окно под CSP и блокировка навигации проверяются
[`tools/verify-ui.mjs`../../tools/verify-ui.mjs). Проверка отмены на живой ноде
требует того же стенда, что и крэш-тесты, поэтому перенесена в фазу 1.

## Фаза 0.5 — нода: закрыть API (P0, вне очереди)

Найдено при разборе исходников `grin 5.5.2`. `grin server config` пишет пути к
`.api_secret`/`.foreign_api_secret`, но сами файлы не создаёт; `grin server -c …`
минует `initial_setup_server`, где они создаются; при отсутствии файла
`get_first_line` возвращает `None`, и `node_apis` не включает Basic-auth. Итог:
`/v2/owner` и `/v2/foreign` открыты на loopback, CORS `*`, а `--api_port`
переводит API на `0.0.0.0`. Через owner-API доступны `reset_chain_head`,
`invalidate_header`, `compact_chain`, `validate_chain`, `ban_peer`; через
foreign — `receive_tx`/`build_coinbase`. Ключи и seed в ноде не лежат, но
целостность цепи и доступность — под угрозой.

Это не будущая функция, а дыра в текущих сборках, поэтому фаза идёт до фазы 1.

- **Секреты.** Создавать owner-секрет до первого старта: 32 байта hex,
 `create_new`, ACL «только текущий пользователь»; путь проверять, битый файл —
  перегенерировать. `.foreign_api_secret` намеренно не создаётся: `/v2/foreign`
  у ноды read-only и нужен кошелькам (иначе 401); кошельки получают
 `node_api_secret_path` на owner-секрет.
- **Fail-closed.** После старта: `get_status` без `Authorization` → `401`,
  с неверным → `401`, с секретом → `200`. Если без секрета `200` — не открывать
  кошелёк и показывать ошибку; тихого отката быть не должно.
- **Только loopback.** Валидировать `api_http_addr` как `127.0.0.1:<port>`;
  отказывать на `0.0.0.0`, `::`, hostname. Никогда не использовать `--api_port`.
- **CORS.** API ноды — локальный admin, а не браузерный. Либо локальный прокси,
  который проксирует только `/v2/owner` с auth и срезает `Origin`/CORS, либо
  явный запрет браузерного доступа; `Access-Control-Allow-Origin: *` не оставлять.

**Сделано в 0.1.44/0.1.47:** owner-секрет создаётся до старта, fail-closed,
только loopback; живьём проверено: 401 без auth и 200 с ним. Развязка:
owner API защищён, foreign API оставлен открытым (read-only) и нужен кошелькам,
поэтому кошельки получают `node_api_secret_path` на owner-секрет.
CORS закрыт локальным прокси в 0.1.54 (внутренний порт ноды + срезающий
заголовки прокси); остаток — внешняя/ручная нода, см. STATUS.

**Гейт:** свежая портативная сборка без секретов: старт; запрос без
`Authorization` → `401`; неверный секрет → `401`; верный → `200`; `api_http_addr`
только loopback; owner-метод нельзя выполнить из браузера.

**Смежное:** абсолютные пути в `grin-server.toml` (перенос портативной папки) —
фаза 4; `child.kill()` вместо graceful Ctrl+C — гейт фазы 1 и фаза 4.

## Фаза 1 — журнал транзакций и восстановление после сбоя — почти закрыта

**Срез 1 (2026-10-23):** состояния транзакции (`prepared → locked →
response_received → finalized_not_posted → posted`), запрет повторной подписи и
повторная публикация через `get_stored_tx` — сделано и покрыто юнит-тестами, см.
[STATUS.md](../status/STATUS.md#фаза-1-срез-1--журнал-состояний-и-повторная-публикация).

**Срез 2 (2026-10-23, по внешнему аудиту 0.1.6):** `finalizing` как намерение перед
подписью, сохранение записи при неудачной отмене (`failed_recoverable`), проверка
tx-log перед повторной публикацией, диагностика нечитаемых pending, автосверка при
разблокировке — см.
[STATUS.md](../status/STATUS.md#фаза-1-срез-2--исправления-по-аудиту-016).
Осталось по срезу 2: см. актуальный список в «Срезе 3» ниже.

**Срез 3 (0.1.33–0.1.51):** крэш-границы RPC и embedded пройдены, ответный
slatepack шифруется в обоих бэкендах, суммы сверяются с цепью, `live_testnet`
прогнан вручную (0.1 GRIN, подтверждение и отмена), `republish` добавлен,
пароли зануляются. Осталось: регрессионные тесты денег в CI, kill ноды и
рестарт без потери журнала, graceful `stop`.

- Состояния журнала: `PREPARED → LOCKED → RESPONSE_RECEIVED → FINALIZING →
  FINALIZED_NOT_POSTED → POSTED`, плюс `FAILED_RECOVERABLE`; запись в журнал до
  каждого необратимого шага. `CONFIRMED`/`CANCELLED` журнал не дублирует — они
  живут в tx-log.
- `finalize` и `post` идемпотентны: повтор после крэша не подписывает и не
  блокирует заново.
- Импорт seed-фразы в **пустой** каталог (`restore`), без перезаписи существующего.
- Приём: «ответ отправлен» ≠ «деньги получены»; сверка входящего выхода с цепью
  перед показом подтверждённого баланса.

**Гейт:** крэш-тесты во всех точках перехода, дубликаты ответов, повторный
broadcast, отмена во время финализации; отдельно — kill ноды и рестарт: цепь и
pending не потеряны, входы не залипли. `NodeManager::stop` сейчас делает
`child.kill()` (TerminateProcess), поэтому graceful Ctrl+C — отдельный пункт
фазы 4.

## Фаза 2 — доверие к ноде и восстановление UTXO — в работе

**Срез 1 (2026-10-23):** фазы ноды `not_running / starting / headers / blocks /
ready / unknown`, `synced` только для `ready`, запрет отправки до готовности —
см. [STATUS.md](../status/STATUS.md#фаза-2-срез-1--статус-ноды). Скан UTXO с прогрессом
сделан в 0.1.38; в 0.1.69 лог-эвристика заменена явными состояниями
`not_started/running/completed/failed` (процента больше нет), добавлены единый
`NodeSnapshot` (endpoint/auth/network/min_confirmations), пересоздание RPC
backend при смене endpoint, проверка свежести tip, отмена RPC-скана
(kill процесса → `failed` → перезапуск backend) и embedded-скана (кооперативно
между батчами через публичный API libwallet, без kill)
([SPIKE_EMBEDDED_SCAN_CANCEL.md](../historical/SPIKE_EMBEDDED_SCAN_CANCEL.md)). Живой
endpoint-switch, смена сети в пустом временном каталоге, graceful stop и
реальный Tor bootstrap/остановка проверены; остался живой прогон с реальным
mainnet-кошельком/сетью.

- Источник статуса синхронизации: RPC (`get_status`) плюс пиры; лог-эвристика —
  только дополнение, не истина.
- **Личность и сеть ноды.** Проверять `chain` (`test`/`main`), `user_agent`
  (`MW/Grin 5.5…`) и `connections`; `no_sync` + непустой tip — не доказательство
  готовности: потеряв пиров, нода остаётся с устаревшим tip. Для `ready` нужен
  хотя бы один живой пир и сравнение высоты с `get_connected_peers` (или свежий
  прогресс). `get_status` — только с auth (фаза 0.5).
- **Ложная нода.** `wait_for_api` проверяет только TCP-connect; локальный сервис
  на порту ноды может выдать себя за неё. Секрет из фазы 0.5 — обязательное
  доказательство личности; без него `ready` не выставлять.
- Блокировка сканирования и траты, если нода недоверенная/несинхронизированная,
  с однозначным сообщением.
- Полное восстановление (`scan`): явные состояния без процента; отмена есть у
  обоих бэкендов: RPC — kill отдельного процесса, embedded — кооперативно между
  батчами через публичный API libwallet, без kill и без патча vendor.
  Восстановленные выходы отделены от истории транзакций, которая может быть
  невосстановима.
- Подключение к уже запущенной ноде вместо запуска второй: 
ode.state` + проверка
 `get_status` (предусловие фоновой ноды).

**Гейт:** восстановление известных testnet-средств только из фразы в чистый
каталог, с независимой проверкой адреса и баланса; `ready` не включается на
 `no_sync` с нулём пиров и на ноде с чужой сетью.

## Фаза 3 — защита seed и миграция

Дизайн и тест-план: [ARGON2ID.md](../historical/ARGON2ID.md). Срезы 1–2 (конверт для новых
кошельков и разблокировка встроенного бэкенда) — 0.1.68, срезы 3–5 (RPC-бэкенд,
mainnet-гейт, миграция legacy по кнопке, Argon2id для ключа истории) — 0.1.69,
всё без релиза. Kill-дрилл M0–M5 и адверсариальное ревью проведены
([REVIEW_MIGRATION.md](../historical/REVIEW_MIGRATION.md)). Осталось: внешнее человеческое
ревью миграции, живой прогон с нодой, обрыв питания и межпроцессная блокировка.

- Версионированный аутентифицированный конверт на Argon2id с калиброванными
  параметрами. Derivation Grin, транзакционная криптография и список слов не
  меняются.
- **Ограничение upstream, которое определяет архитектуру:** `grin-wallet`
  перезаписывает `wallet.seed` своим KDF при смене пароля
  ([seed.rs:289../../vendor/grin_wallet_impls/src/lifecycle/seed.rs#L289) — PBKDF2,
  100 итераций). Значит патчить `seed.rs` на месте нельзя: нужен отдельный файл
  конверта, изолированный legacy-адаптер и подача seed в upstream через временный
  файл со случайным паролем (или через API без файла, если он есть в 5.5).
  Проверить это до начала работ.
- Миграция: обязательный зашифрованный бэкап, проверка читаемости, атомарная
  замена, откат, тест разблокировки после миграции. Открытый seed на диск не
  попадает ни на одном шаге.
- Смена пароля, восстановление забытого пароля через фразу, Unicode-пароли,
  зануление буферов.

**Гейт:** независимое ревью миграции, тест-векторы Argon2id, негативные кейсы,
обрыв питания в каждой точке, совместимость со старым `wallet.seed`.

## Фаза 4 — оболочка

- IPC: capability `main` + `freezePrototype` — сделано в 0.1.51; allowlist
  навигации и отсутствие удалённого контента — сделаны. Собственные команды в

- Обновления: сохранение данных перед автообновлением, отделение данных WebView2
  от криптографических данных, откат.
- Подпись артефактов, происхождение, SmartScreen/Defender.
- Секрет owner API (`/v2/owner`) обязателен; foreign API — только loopback.
  Конкретика и P0-фикс — фаза 0.5: создание файлов секретов, проверка `401`,
  ACL, запрет `0.0.0.0`/`--api_port`, CORS. До закрытия фазы 0.5 эта строка
  считается невыполненной, даже если клиент умеет присылать `Authorization`.
- **Портативность и остановка ноды.** `grin server config` пишет абсолютные
 `db_root` и пути секретов; после копирования/переноса папки проверять и
  переписывать пути. Остановка — graceful Ctrl+C, а не `TerminateProcess`
  (`child.kill()`), иначе крэш-тест фазы 1 проверяет не тот сценарий.

**Гейт:** модель угроз и пентест оболочки; подписанная сборка проходит проверку
на чистой Windows 10/11.

## Миграция на официальный grin-wallet — архитектурное решение 2026-10-23

Задача: Flint перестаёт быть кошельком и становится GUI поверх официального
`grin-wallet.exe`. Нода остаётся `grin.exe`, кошелёк — отдельный процесс с owner
API. Разведка протокола: [SPIKE_GRIN_WALLET_API.md](../historical/SPIKE_GRIN_WALLET_API.md).

**Уже проверено:** `grin-wallet 5.5.1` (SHA256 сверен), запуск `owner_api` без
пароля, `/v3/owner` с Basic-аутентификацией, обязательная ECDH+AES-GCM сессия,
наличие всех нужных методов.

**Этапы:**

1. **Клиент `wallet_rpc`** в `flint-core`: ECDH-хендшейк, AES-256-GCM, вызовы
  `open_wallet`/`summary`/`txs`/`send`/`receive`/`scan`. Интеграционный тест
   против реального бинаря.
2. **Параллельный бэкенд** за флагом (`--backend=grin-wallet`): старый код
   остаётся рабочим, пока новый не пройдёт те же живые сценарии.
3. **Переключение GUI** на RPC: пароль → `open_wallet`, статусы из tx-log,
   slatepack-операции через `slate_*` методы.
4. **Удаление** `grin_wallet_*`, нашего журнала и слате-кода; остаются супервизор,
   нода, UI, диагностика.
5. **Упаковка**: два бинарника (нода + кошелёк), два порта, автозапуск кошелька
   как сервиса.

**Гейт:** тот же живой сценарий (два кошелька, send → receive → post → подтверждение,
отмена, крэш) проходит на новом бэкенде; старая сборка остаётся как откат.

**Риски:** шифрование сессии (тесты против реального бинаря), секрет owner API,
пароль только через `open_wallet`, совместимость версий ноды и кошелька 5.5.x.

**Мобильные:** iOS/Android не могут запускать `grin-wallet.exe` как процесс. Там
нужен встроенный кошелёк на тех же крейтах, поэтому интерфейс бэкенда
проектируется под две реализации (процесс и библиотека) с самого начала, иначе
мобильная версия упрётся в тупик.

## Фоновая нода — отдельная задача после фазы 5

Идея: нода синхронизируется постоянно, а кошелёк при запуске просто подключается к
готовой цепи. Полезно, но не «галочка в настройках»: сначала нужны три
предусловия, иначе получаем конфликт портов и два процесса на одном `chain_data`.

**Предусловия (обязательны до реализации):**

1. **Один владелец данных.** Эксклюзивная блокировка `<data>/<network>/node.lock`:
   второй процесс с той же цепью обязан не стартовать, а подключиться.
2. **Подключение к уже запущенной ноде.** Кошелёк при старте читает 
ode.state`
   (pid, порт, сеть, версия), проверяет `get_status` и **не спавнит** свою ноду,
   если чужая жива и совпадает по сети. Сегодня приложение всегда пытается
   запустить свою — отсюда «порт занят» и работа через чужой узел.
3. **Секрет для owner API.** Сейчас `/v2/owner` отвечает без аутентификации
   (файла `.api_secret` нет), а через него доступны `ban_peer`, `compact_chain`,
  `reset_chain_head`. Для постоянно живущей ноды это недопустимо; закрывается
   в фазе 0.5, до фонового демона. Секрет обязателен, foreign API — только loopback.

**Дизайн:**

- Режим `Flint.exe --node-daemon`: супервизор, который держит `grin` и пишет
 
ode.state`; ставится в автозапуск пользователя (HKCU Run / планировщик), без
  службы Windows и без прав администратора — портативность «удалил папку = удалил
  всё» сохраняется.
- Настройки: «Держать ноду запущенной в фоне», «Запускать при входе в Windows»,
  «Остановить ноду при выходе» (по умолчанию — да, как сейчас).
- Переключение testnet/mainnet: сначала остановить текущую ноду и дождаться
  выхода, только потом менять сеть. Две ноды на разных сетях одновременно — нельзя.

**Риски, которые надо закрыть в дизайне:** трафик и диск при синхронизации без
ведома пользователя (нужен индикатор и пауза), обновление `grin.exe` при
запущенной ноде (файл залочен), осиротевшие процессы после падения, удаление
портативной папки при живом демоне.

**Гейт:** кошелёк закрыт и открыт — нода та же, повторной синхронизации нет; две
копии приложения не поднимают две ноды; mainnet не стартует случайно; секрет
owner API обязателен и проверен.

## Мессенджер для slatepack — отдельный трек (после стабилизации кошелька)

Цель: пользователи Flint (и других кошельков) обмениваются сообщениями и
slatepack-ами напрямую, без копирования armor-блоков через мессенджеры общего
назначения. Модуль должен быть **переносимым**: протокол + SDK, а не функция,
вшитая в UI Flint.

### Границы

- **Не** заменяет ноду и не хранит ключи: только транспорт сообщений.
- **Не** является анонимным мессенджером общего назначения: полезная нагрузка —
  slatepack и короткие служебные сообщения, без вложений и групп на старте.
- Требует **внешней инфраструктуры** (relay), поэтому включается только явно и
  должна иметься возможность self-host.

### Фазы

**M1 — протокол и SDK.**
- Идентичность = slatepack-адрес (`tgrin1…`/`grin1…`); подпись сообщений ключом,
  производным от адреса, чтобы получатель проверял отправителя.
- E2E-шифрование к адресу получателя; plaintext-slatepack (`manual`) **не
  пересылается** через relay вообще.
- Конверт сообщения: версия, id, адрес получателя, nonce, ciphertext, подпись,
  TTL. Спецификация в `docs/`, версионирование по `version`.
- SDK: Rust-крейт `flint-messenger` с трейтами `Transport` + `Store`, чтобы
  подключаться к любому кошельку (Grin++, Grim, Niffler) без переписывания.

**M2 — desktop-интеграция.**
- Отправка/приём slatepack из окна «Получить/Отправить» одним действием,
  очередь недоставленных, статусы «отправлено/доставлено/прочитано».
- Локальное хранилище переписки в зашифрованном виде (тот же конверт, что для
  seed-данных), очистка по TTL.

**M3 — прямой onion + relay для офлайна.**
- Прямой onion: onion из адреса, gateway за hidden service, `DirectOnionTransport`;
  работает, когда получатель онлайн. **Сделано 0.1.65.**
- Store-and-forward relay: `flint-relay` — отдельный бинарь без кошелька, TTL,
  квоты, диск, подписанный ack. **Сделано 0.1.66.** Нет PoW/распределённого
  rate limit.
- Метаданные: relay не должен знать содержимое; знает только адрес получателя и
  размер/время. Прямой onion вообще не требует relay.
- Развёртывание публичного relay: один бинарь + Postgres/SQLite; self-host
  инструкция (`docs/operations/RELAY.md`). **Код готов, публичный инстанс — осталось.**

**M4 — мобильные приложения (iOS/Android).**
- Общий Rust-ядро: кошелёк + messenger SDK, тонкие нативные оболочки
  (Tauri 2 mobile или Swift/Kotlin UI).
- **Важное архитектурное следствие:** на мобильных нельзя запускать
 `grin-wallet.exe` как процесс — там нужен **встроенный** кошелёк (наши
 `grin_wallet_*` крейты), то есть десктопный бэкенд на `grin-wallet` и мобильный
  на библиотеке должны сосуществовать за одним интерфейсом. Это надо заложить в
  этап 1-2 миграции, иначе мобильная версия упрётся в тупик.
- Фоновая доставка: push (APNs/FCM) как «разбудить и забрать», без содержимого
  сообщения в push; фоновая синхронизация кошелька — по возможности ОС.
- Секреты: Keychain/Keystore, биометрия для разблокировки, запрет бэкапа seed в
  iCloud/Google Backup.

### Гейты

- M1: спецификация + SDK с тест-векторами; два независимых клиента обмениваются
  сообщением через тестовый relay.
- M2: живой обмен slatepack между двумя кошельками без ручного копирования.
- M3: прямой onion-обмен без relay (0.1.65); standalone relay с TTL, квотами,
  диском и подписанным ack (0.1.66). Осталось: публичный инстанс, PoW/rate
  limit, пентест на метаданные.
- M4: сборки в TestFlight/Internal testing, приём платежа на телефоне, сообщение
  доставляется при закрытом приложении.

### Открытые вопросы (решить до M1)

**Решения (2026-10-24):**

1. **Транспорт — только собственный relay.** Nostr/Matrix как готовый слой не
   берём: метаданные и зависимость от чужих операторов unacceptable.
2. **Полезная нагрузка — и сообщения, и slatepack-и.** Не только armor-блоки.
3. **TTL по умолчанию 26 часов, настраиваемо.** Ориентир — сутки жизни slate
   плюс запас на доставку.
4. **Мобильный MVP — после десктопа**, отдельной реализацией (встроенный кошелёк,
   не процесс `grin-wallet`).
5. **Транспорт — Tor/arti, адрес = onion.** Slatepack-адрес (`grin1…`) — это
   ed25519-ключ; из него **детерминированно** выводится Tor v3 onion
   (`OnionV3Address::from_private`, `vendor/grin_wallet_util/src/ov3.rs`).
   Upstream `grin-wallet listen` уже поднимает onion именно из адресного ключа
   (`controller/src/controller.rs`) и принимает slate на foreign API — то есть
   «знаю адрес → отправляю как в BTC» работает без relay, когда получатель онлайн.
   Iroh/libp2p не нужны: их роль выполняет Tor.
6. **Relay остаётся только как mailbox** для офлайн-получателя и как fallback,
   когда onion недоступен. Формат сообщения один и тот же, меняется транспорт.

## Фаза 6 — релиз

Pinned reproducible-сборки, SBOM, сканер уязвимостей, подписанные артефакты,
теги, тесты на нехватку диска, битую цепь, офлайн, флапающую сеть, аварийное
завершение. Внешний аудит и письменное ревью модели угроз.

**Гейт:** только после этого — обозначение сборки пригодной для реальных средств.
До него в UI и README остаётся предупреждение из шапки STATUS.md.

## Заморожено

**Janus.** Публичного протокола нет, модели угроз нет, ревьюировать нечего.
Код остаётся демонстрационным, реальные XMR/GRIN свопы не включаются и не
рекламируются до публикации спецификации. Силы в него не вкладываются.

**QR-код адреса.** После фазы 4; не влияет на безопасность средств.

## 2. SENT-02 — `restrict()` не удаляет чужие явные ACE

### Код

`crates/core/src/win_acl.rs:24-32` вызывает:

```text
icacls <path> /inheritance:r /grant:r <USERNAME>:F
```

Успех процесса считается успешным ограничением. Дополнительной проверки итогового
DACL нет. Комментарий и вызывающий код описывают результат как owner-only.

### Динамическая проверка

На одноразовом `.tmp/sentinel-acl-probe.txt`, без секретов:

1. Отключено наследование и явно выдано `Everyone:F` (`*S-1-1-0`).
2. Выполнена та же команда с `/inheritance:r /grant:r <USERNAME>:F`, что в helper.
3. Итоговый SDDL получен через `Get-Acl`:

```text
O:S-1-5-21-...-1001G:S-1-5-21-...-1001D:PAI(A;;FA;;;WD)(A;;FA;;;S-1-5-21-...-1001)
```

`WD` — Everyone. Право Everyone осталось; `P` подтверждает защищённый DACL, то есть
это не просто продолжение прежнего наследования. Логи:
`.tmp/sentinel-acl-probe.log` и `.tmp/sentinel-acl-probe-sddl.log`.

### Вывод и границы

Дефект подтверждён для явно существующего ACE. Это не утверждение, что каждый новый
файл доступен Everyone: при обычном наследовании опасные ACE могут отсутствовать.
Однако helper не выполняет заявленный контракт для уже существующих/переиспользуемых
файлов. Все fail-closed вызовы, включая seed, полагаются на недостаточную проверку.

**Приёмка исправления:** тест начинает с постороннего explicit ACE; после restrict
effective DACL содержит только утверждённый allowlist. Нужна проверка результата,
а не только exit code `icacls`. Политика для SYSTEM/администраторов должна быть
явно выбрана и задокументирована. Второй реальный Windows-аккаунт остаётся отдельным
приёмочным тестом.

## 3. SENT-01 — подтверждённые места и пропущенная область

### Перечисленные Sentinel места

- `core/src/node.rs:454-458`: `.api_secret` и `.foreign_api_secret` записываются до
  `restrict`; ошибка отбрасывается через `let _`.
- `core/src/rpc_backend.rs:184-193`: upstream создаёт `.owner_api_secret`; Flint
  читает секрет, подавляет ошибку ACL и продолжает запуск.
- `core/src/onion.rs:38-40`: `hs_ed25519_secret_key` записывается до подавляемого
  `restrict`.
- `core/src/service.rs:2132-2152`: plaintext pending записывается и переименовывается;
  ошибка конечного `restrict` подавляется.
- `core/src/config.rs:413-417`: ошибка ACL corrupt-копии settings подавляется.
  Это уже было отмечено в предыдущем F-05, поэтому данная строка не новая.

### Дополнительно найдено при проверке

1. **`.node_api_secret`, bearer credential.** `core/src/rpc_backend.rs:395-402`
   сначала записывает секрет во временный файл, затем применяет `restrict`.
   После rename конечный файл не проверяется. Окно записи до ACL и риск SENT-02
   применимы, хотя Sentinel это место не перечислил.
2. **Архив pending вообще без `restrict`.** `core/src/service.rs:2175-2193` пишет
   plaintext slate в `archive/`, делает rename и удаляет исходную запись. Даже
   подавляемого вызова ACL нет.
3. **History key.** `runtime/src/history.rs:385-420` подавляет ошибку ACL и temp, и
   конечного файла. Сами байты обёрнуты паролем, поэтому это не эквивалент раскрытию
   raw seed, но заявленная локальная защита не гарантирована.
4. **Blocked list.** `runtime/src/messenger.rs:476-485` записывает адреса до ACL и
   подавляет ошибку. Это преимущественно privacy/integrity-риск, не равный по
   тяжести раскрытию API/onion-секрета.

### Оценка приоритета

P1 оправдан для API/onion/seed-контура из-за возможного раскрытия учётных данных
другому локальному principal. Эксплуатация реальным вторым аккаунтом не выполнялась;
P1 не означает доказанную удалённую компрометацию. Для history/blocked/corrupt
нужна явная политика по тяжести, но молчаливый fallback недопустим.

### Требование к исправлению

Сначала исправить SENT-02, иначе обработка `Result` даст ложное ощущение защиты.
Затем централизовать secure write/existing-file validation. Для seed/API/onion —
fail-closed; для pending/history/blocked/corrupt — явно принятая политика с ошибкой
или постоянным пользовательским предупреждением. Upstream-created
`.owner_api_secret` требует отдельного дизайна: нельзя механически применить helper,
рассчитанный только на файлы, которые Flint создаёт сам.

## 4. F-04 — подтверждённый повтор

Embedded `core/src/service.rs:1816-1857` и RPC
`core/src/rpc_backend.rs:1520-1566` сохраняют intent до `receive_tx`, response —
после возврата. Crash между мутацией и durable response оставляет запись без ответа;
повторный receive блокируется. Новых доказательств восстановимости отчёт не даёт.

Полезное уточнение Sentinel — проверить на реальном testnet Slate, может ли
`get_stored_tx`/tx-log восстановить именно response. Это исследовательская задача,
а не основание понизить F-04. До probe действует прежний P1. R-01 также остаётся:
оба backend переводят слишком широкий класс ошибок в `ResponseLost`/`lost`.

## 5. F-10 — подтверждено с уточнениями

Независимая read-only проверка была делегирована локальному Codex; его выводы
сверены с указанными файлами основным исполнителем. Итог Codex:
`.tmp/codex-sentinel-f10-output.md`, JSONL:
`.tmp/codex-local/run-20261027-030608-271.jsonl`.

- `tools/fetch-wallet.ps1:15-35` берёт ZIP и checksum из одного release; локального
  независимого expected SHA-256 при fetch нет.
- `tools/package-slint.ps1` проверяет четыре EXE из manifest, но дополнительно
  копирует `vcruntime140.dll` и `pt_config.json` вне этого manifest.
- `tools/sbom.ps1` строит components только из `cargo metadata`; native assets,
  их происхождение и хеши отсутствуют.
- `tools/release.ps1:67-69` уже содержит вызов подписи с `/tr` и `/td sha256`.
  Поэтому timestamp-механизм существует; открыты сертификат, реальная подпись и
  обязательное применение. Без `-RequireSigned` unsigned release допускается.
- `tools/verify-native-assets.ps1` существует, но не заменяет расширение manifest и
  не включён как самостоятельный обязательный шаг CI/release.

F-10 остаётся P2 release/supply-chain, а не новой денежной P1.

## 6. Автоматические срабатывания

По указанным строкам решения Sentinel разумны:

- `node.rs:448` — позиция `insert_str` в TOML, не SQL.
- `seed/store.rs:1496` и testnet RPC/live-тесты — одноразовые тестовые пароли;
  реальные секреты и необходимость ротации не обнаружены.
- `runtime/tests/rpc_lifecycle.rs:130` относится к обычному unit-тесту с временным
  кошельком, остальные указанные строки — ignored live-тестам с временными данными.

Сам запуск плагина, 95 файлов и полнота девяти срабатываний независимо не
воспроизводились. Поэтому подтверждается ручная классификация приведённых примеров,
а не метрика покрытия сканера.

## 7. Актуальный порядок действий

1. **SENT-02:** исправить и динамически проверить сам owner-only ACL примитив.
2. **SENT-01/F-05:** устранить подавление ошибок и write-before-ACL во всех найденных
   местах, включая archive/`.node_api_secret`/history/blocked.
3. **F-01/R-01:** завершить безопасные денежные переходы.
4. **F-04:** исследовать upstream recovery, затем реализовать доказанное решение или
   fail-closed recovery runbook; live crash-матрица обязательна.
5. **F-10 и внешние гейты:** pins, native+Cargo SBOM, RustSec/OSV, подпись, второй
   Windows-аккаунт, FAT/exFAT, нагрузочный и человеческий pentest.

Не выполнялись в этой проверке: изменение кода, live/mainnet, второй аккаунт,
FAT/exFAT, SCA, flood, power-loss/disk-full и новый полный test suite (код не менялся).

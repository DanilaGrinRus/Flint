доверия/mainnet. Изменения исходного кода не выполнялись.

> Это внутренний статический и ручной code review, а не внешний человеческий
> аудит или pentest. Решение MAINNET_READINESS не меняется: реальные средства
> запрещены до закрытия установленных гейтов.

## 3. SENT-01 — P1: ошибки защиты файлов подавляются

**Статус: подтверждено чтением кода. Эксплуатация на втором Windows-аккаунте и
на FAT/exFAT в этой сессии не проверялась.**

`win_acl::restrict()` специально возвращает ошибку, однако часть вызывающего кода
отбрасывает её через `let _ = ...`. Комментарий `win_acl.rs` допускает продолжение
с предупреждением, но в перечисленных местах предупреждения также нет.

| Место | Данные | Последствие при ошибке ACL |
|---|---|---|
| `core/src/node.rs:454-458` | `.api_secret`, `.foreign_api_secret` | Секреты создаются/используются без гарантии owner-only доступа. |
| `core/src/rpc_backend.rs:188-193` | `.owner_api_secret` | RPC продолжает запуск после неуспешного ограничения доступа. |
| `core/src/onion.rs:38-40` | `hs_ed25519_secret_key` | Приватный ключ onion может сохранить наследованные права; возможна компрометация identity/перехват на локальном хосте. |
| `core/src/service.rs:2150-2152` | pending/slate-записи | Суммы, адреса и структура сделок могут быть доступны другим локальным пользователям. |
| `core/src/config.rs:414-416` | повреждённая копия settings | Копия потенциально содержит `node_api_secret`, но ошибка ACL скрыта. |

Отдельно есть окно «сначала секретные байты, затем ACL» в `node.rs` и `onion.rs`.
Даже возврат ошибки после записи сам по себе не устранит это окно.

**Исправление.**

1. Ввести единый helper для секретных файлов: создать пустой temp-файл → применить
   ACL → записать и синхронизировать → атомарно переименовать → проверить ACL
   конечного файла. Для существующего секрета применять ACL до использования.
2. Для seed/API/onion-секретов ошибку ACL считать фатальной: не запускать
   соответствующий backend и не оставлять новую незащищённую копию без обработки.
3. Для pending и corrupt-копии выбрать явную политику: предпочтительно fail-closed
   до записи; если продолжение разрешено, возвращать постоянное пользовательское
   предупреждение, а не подавлять ошибку.
4. Не раскрывать содержимое файлов в ошибках; путь допустим только в защищённой
   диагностике согласно действующей политике проекта.

**Приёмка.**

- Unit-тест с инжектируемым сбоем ACL для каждого вызова: секрет не используется,
  состояние не выглядит успешным, ошибка не содержит секрет.
- Тест на создание: ACL применяется до записи секретных байтов.
- Ручной тест под вторым Windows-пользователем: чтение секретов и журналов запрещено.
- Отдельный тест на ФС без ACL: понятный отказ, без молчаливого fallback.

## 4. F-04 — P1: crash gap после `receive_tx`

**Статус: известная находка, подтверждена повторным чтением обоих backend.**

Embedded (`core/src/service.rs:1830-1857`) и RPC
(`core/src/rpc_backend.rs:1531-1566`) сохраняют intent до `receive_tx`, но response —
только после возврата и мутации кошелька. Авария между ними оставляет состояние
без durable response. Защита от автоматического повторного receive есть, однако
штатного восстановления самого ответа нет.

Воздействие: отправитель может не получить ответ, а его входы — остаться
заблокированными до отдельного восстановления/отмены. Это не доказательство
необратимой потери seed или монет.

**Порядок закрытия.**

1. Проверить на реальном testnet Slate, может ли upstream tx-log/`get_stored_tx`
   восстановить именно response после `TransactionAlreadyReceived`; не полагаться
   на предположение о формате хранения.
2. Если восстановление возможно — реализовать его для `receive_intent`/`response_lost`
   в обоих backend с проверкой slate id, суммы и участников. Автоматический повтор
   `receive_tx` не использовать.
3. Если невозможно — зафиксировать fail-closed runbook восстановления и безопасную
   координацию новой сделки/отмены; не маскировать это под успешный retry.
4. Добавить failpoint непосредственно после мутации и до durable response: crash,
   ошибка записи, ACL и disk-full для embedded и RPC.

**Приёмка:** после каждого сбоя нет повторной подписи/повторного receive; система
либо возвращает идентичный сохранённый/восстановленный response, либо однозначно
блокирует операцию и ведёт по документированному восстановлению.

## 5. F-10 и зависимости — P2 до публичного релиза

Повторная проверка подтвердила:

- `tools/fetch-wallet.ps1:22-35` получает архив и checksum из одного release;
  независимого pinned SHA-256 в параметрах/источнике нет.
- Packaging сверяет `resources/native-assets.sha256`, но `tools/sbom.ps1` формирует
  SBOM только для Cargo components, без native assets.
- Production-подпись и timestamp остаются внешним релизным гейтом.

**Исправление:** закрепить ожидаемые версии/хэши native assets в доверенном источнике,
проверять их при fetch/package, включить происхождение и хэши всех bundled-бинарников
в SBOM, для production требовать подпись. После согласия на сетевой запрос выполнить
RustSec/OSV по корневому `Cargo.lock`; в текущем аудите SCA не проводился.

## Что реально используется сейчас

`crates/runtime/src/lib.rs:45` создаёт `JanusService::demo(None)` — то есть свопы
живут **только в памяти**, файл не читается и не пишется. Поэтому находки про
персистентность ниже — **латентные**: они не проявляются в текущем runtime, но
становятся блокерами в момент подключения `Some(path)` и реальных средств.

## Опровергнуто проверкой

**`service.rs:193-197`, `write_atomic`: «`fs::rename` на Windows не перезапишет
существующий файл, поэтому второе сохранение не сработает» — неверно.** В Codex эта
находка шла как критичная.

Стандартная библиотека Rust на Windows вызывает `MoveFileExW` с
`MOVEFILE_REPLACE_EXISTING`, поэтому перезапись цели происходит. Проверено отдельным
тестом (`.tmp/rename_check/main.rs`, компиляция `rustc -O`, файл вне репозитория):

```
first: {"v":1}
second: OK, content={"v":2}
tmp exists after second: false
```

Остаточный риск узкий и не про перезапись: `rename` упадёт, если цель удерживает
другой процесс без доступа на удаление, если файл помечен read-only или если цель на
другом томе. Для `swaps.json` рядом с `.tmp` это экзотика, а не блокер.

Тот же результат — причина, по которой находки Codex проверяются по коду: 1 из 7
оказалась ложной, и именно она шла с максимальной серьёзностью.

## Что проверить не удалось

- Семантику равенства `tip == lock_height` относительно консенсусного правила Grin:
  Janus не вызывает код ядра/кошелька, а по условиям ревью он не анализировался.
  Внутри Janus сравнение согласовано (`>=`) и покрыто тестом.
- Реальное двойное расходование или потерю средств: нужен живой прогон на цепи,
  в текущем runtime всё в памяти и помечено как симуляция.
- Гонки и поведение `rename` на живой Windows-ФС под нагрузкой: вывод статический плюс
  один изолированный тест.

## Порядок исправления до подключения реальных средств

1. Персистентность: загружать снимок в `with_parts`; ошибку чтения или разбора
   отдавать явно, а не превращать в пустое состояние; при повреждении не
   перезаписывать исходный файл.
2. Порядок записи: сначала успешное сохранение (или журнал намерений), потом
   публикация нового состояния в памяти.
3. Инварианты состояния: `LockGrin` только из `StampsVerified`, `lock_blocks` сверять
   с `offer.lock`, обязательная `amount` в границах оффера, `RevealSecret` — только с
   проверяемым доказательством.

Пункты 4–6 из таблицы воспроизводятся и в демо-режиме, поэтому их можно закрыть
тестами уже сейчас, не дожидаясь интеграции с кошельком.

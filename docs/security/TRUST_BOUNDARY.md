# Граница доверия Slint ↔ flint-runtime

## Модель

Flint — **один процесс**: Slint UI и `flint-runtime` живут в одном адресном
пространстве, без IPC. `flint-runtime` — единственный слой, который вызывает
`grin-wallet`, node, Tor и messenger; UI получает `WalletRuntime` и вызывает
его публичные методы.

Следствие: это **не** изоляция от вредоносного кода. Если в процесс попал
malware или UI-код скомпрометирован, он видит те же секреты, что и runtime.
Граница нужна для того, чтобы обычные UI-ошибки не обходили проверки и не
работали с сырыми ключами напрямую.

## Проверять в UI-коде

- [ ] UI не вызывает `WalletRpc`/HTTP RPC напрямую, только методы runtime.
- [ ] UI не читает seed-файл и не хранит seed дольше отображения/ввода.
- [ ] Пароли передаются как `Zeroizing<String>` и очищаются после вызова.
- [ ] Ошибки не печатают пароль, seed, slatepack-секреты или полный путь данных.
- [ ] Опасные операции (send/finalize/cancel/password/delete) проходят через
      runtime-проверки, даже если кнопка скрыта.
- [ ] UI не может подменить состояние pending/journal в обход runtime.
- [ ] Slint-свойства не содержат seed/пароль после закрытия модалки.

## Найденные исключения

- Запуск RPC-процесса перенесён из UI в `WalletRuntime::start_rpc_background()`;
  прямого `rpc()` в UI не осталось.
- UI получает seed-фразу при создании/восстановлении для показа пользователю.
  Это неизбежно; строка должна очищаться после закрытия экрана.
- Пароль в поле Slint существует в памяти UI на время ввода. Полностью убрать
  это нельзя без отдельного защищённого ввода; риск ограничен процессом.

## Остаточные риски

- Host malware/другой пользователь с доступом к процессу или `data` может
  прочитать секреты; это не решается границей в одном процессе.
- Core dumps, swap и crash-логи могут содержать чувствительные строки; нужна
  политика отключения дампов для release.
- Slint-строки и ошибки могут попасть в скриншоты/буфер обмена.

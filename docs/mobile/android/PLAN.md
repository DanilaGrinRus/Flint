# Flint для Android — план разработки

Дата: 2026-10-27. Статус: план; реализация и сборка Android в рамках этой работы
не выполнялись. Все пункты ниже открыты. DEV BUILD, не аудирован, не для реальных средств.

## 1. Цель и границы первой версии

Некастодиальный testnet-кошелёк Grin из серии Flint: создание и восстановление,
баланс, адрес, история, ручной обмен Slatepack, подтверждение отправки,
блокировка и безопасное восстановление незавершённых операций.

Первый результат — проверяемый APK для testnet, не публичный mainnet-релиз.
Janus/атомарные свопы, собственная полная нода, Tor/relay, фиатные цены и
автоматическая фоновая подпись не входят в первую версию.

Источники ограничений: [STATUS](../../status/STATUS.md),
[MAINNET_READINESS](../../status/MAINNET_READINESS.md),
[BACKENDS](../../architecture/BACKENDS.md),
[ADR receive recovery](../../security/ADR_F04_RECEIVE_RECOVERY.md).

## 2. Предлагаемая архитектура

Предложение для прототипа: Kotlin + Jetpack Compose, ViewModel и coroutines;
денежная логика — Rust-библиотека с тонкой JNI-границей. Это проектное решение,
а не утверждение о существующей Android-реализации.

```text
Compose UI → ViewModel → WalletService → JNI → Rust wallet/domain → внешняя Grin-нода
                                           ↘ Android storage / Keystore
```

- Общее ядро: суммы, адреса, Slatepack, проверка сети, состояния транзакций,
  журналирование, recovery и изоляция кошельков.
- Android-слой: жизненный цикл, биометрия, хранение ключа шифрования,
  файловый обмен, QR, разрешения и уведомления.
- Slint, Windows ACL, запуск grin-wallet.exe и Windows NodeManager в APK не переносятся.
- Нода в первой версии внешняя; приложение не передаёт ей seed и не делает серверную подпись.
- Источник grin-wallet, его commit и патчи должны совпадать с согласованной
  мобильной базой. Одного совпадения номера 5.5.1 недостаточно.
- В JNI нет приватных ключей в JSON-ошибках; handles имеют явный жизненный цикл,
  вызовы сериализованы, память освобождается определённой стороной. Паника Rust
  не должна проходить через границу JNI.
- Суммы передаются целым числом наногрин с проверкой переполнения, без Double.

Подключение нативных библиотек через JNI и Android NDK описано в
[официальной документации NDK](https://developer.android.com/ndk/guides).

## 3. Этап 0 — база и технический прототип

- [ ] Сохранить контрольные снимки desktop/iOS; записать версии, hashes и
      незавершённые изменения до выделения общей библиотеки.
- [ ] Принять ADR о границах ядра: выделение платформенно независимой части
      Flint либо другой способ повторного использования без копии денежной логики.
- [ ] Согласовать лицензирование общего кода: Flint GPL-3.0-only и текущая
      декларация Apache-2.0 в iOS FFI требуют явного решения до переноса файлов.
- [ ] Выбрать отдельное место Android-исходников; `docs/mobile/android` оставить
      каталогом документации. Не включать проект в родительский Cargo workspace случайно.
- [ ] Зафиксировать Rust, JDK, Gradle, Android SDK/NDK и зависимости. Min SDK
      и target SDK утвердить по матрице устройств и требованиям канала доставки.
- [ ] Собрать библиотеку для arm64-v8a и тестового эмулятора x86_64; проверить
      сборку всех нативных зависимостей Grin, загрузку JNI и простую read-only операцию.
- [ ] Описать получение и фиксацию новых зависимостей без нарушения desktop offline-сборки.

Гейт: JNI загружается на эмуляторе и реальном arm64-устройстве; сборка повторяется
в CI, регрессия desktop проходит. Отчёт содержит точные версии и ограничения.

## 4. Этап 1 — создание, восстановление и защита данных

- [ ] Создание нового testnet-кошелька, показ фразы и проверка её резервной копии.
- [ ] Восстановление поддерживаемой фразы средствами grin-wallet: формат и
      число слов брать из реального контракта, не вводить собственную криптографию.
- [ ] Зашифрованный контейнер seed и чувствительных данных в приватном каталоге;
      ключ шифрования защищать Android Keystore. Seed не хранить открытым в настройках.
- [ ] Определить парольное восстановление и поведение при потере/инвалидации
      Keystore-ключа: отказ открытия не должен создавать новый кошелёк поверх старого.
- [ ] Биометрия на открытие и подпись, автоблокировка, закрытие Rust-сессии;
      проверить сон, поворот, уход в фон и завершение процесса системой.
- [ ] Исключить секреты из логов, crash-отчётов, резервного копирования ОС,
      скриншотов и превью недавних приложений; clipboard использовать только явно.
- [ ] Описать ограничения очистки секретов в управляемой памяти Kotlin/JVM.

Android Keystore хранит криптографические ключи; seed хранится отдельно в
зашифрованном контейнере. Основание —
[Android Keystore](https://developer.android.com/privacy-and-security/keystore).
Аппаратную защиту проверять на устройстве; не считать её гарантированной для всех моделей.

Гейт: после перезапуска открывается тот же кошелёк; неверный пароль, потеря
ключа и отмена биометрии безопасно отклоняются. Restore в чистый каталог даёт
тот же адрес; секреты не обнаружены в проверенных логах и экспортируемых файлах.

## 5. Этап 2 — нода и интерфейс кошелька

- [ ] Testnet по умолчанию, явная проверка соответствия сети кошелька и ноды.
      Ошибка сервиса отображается как ошибка, без переключения в mock.
- [ ] Настройка своей ноды, сетевые timeout и отмена операций; секрет ноды
      не сохранять в открытом виде и не передавать в диагностические сообщения.
- [ ] Read-only обновление баланса, высоты и истории; stale-данные явно помечены.
- [ ] Экран портфеля, приёма, отправки, истории и настроек; единый мятный акцент
      из DESIGN.md, суммы моноширинные с табличными цифрами.
- [ ] Никаких длительных Rust/сетевых операций в UI-потоке; повторное нажатие
      не создаёт вторую операцию. Устаревший результат другой сессии отбрасывается.
- [ ] Проверить русский текст, крупный шрифт, TalkBack и разные размеры экрана.

Гейт: значения сверены с независимым запросом к testnet; offline, ошибка сети
и смена ноды не создают ложное состояние готовности или потери данных.

## 6. Этап 3 — полный денежный цикл и recovery

- [ ] Send → S1 → receive → S2 → finalize → post → подтверждение в цепи.
- [ ] До подписи показать адрес полностью, сумму, комиссию и итог; проверить
      spendable и адрес, запросить явное подтверждение получателя.
- [ ] Разделить подготовку, подпись, публикацию и подтверждение; неизвестный
      исход не превращать в Posted. Повтор post не вызывает повтор finalize.
- [ ] Перенести согласованный receive recovery: сохранение подписанного S2,
      точный повтор возвращает тот же ответ; изменённый S1 отклоняется.
- [ ] Журналировать intent/результаты атомарно; ошибки записи не подавлять.
- [ ] Проверить отмену только в допустимых состояниях, locked outputs,
      конфликт, reorg, дубли входящих сообщений и повреждённый Slatepack.
- [ ] Файловый импорт/экспорт через системный выбор, ограничения размера и
      проверка содержимого. QR/сканер и ссылки добавить после базового roundtrip;
      входящая ссылка никогда сама не подписывает транзакцию.

Гейт: desktop ↔ Android в обе стороны на testnet, затем Android ↔ iOS после
готовности iOS UI. Kernel подтверждён в цепи; баланс и отсутствие дублей сверены.
Сборка или screenshot отдельно не являются доказательством денежного цикла.

## 7. Этап 4 — испытания мобильного жизненного цикла

- [ ] Прерывание процесса до/после записи журнала, подписи и post;
      повторное открытие и безопасное продолжение без повторной подписи.
- [ ] Недостаток места, отказ записи, повреждение контейнера/журнала;
      старая пригодная запись и seed сохраняются либо выдаётся явный отказ.
- [ ] Смена Wi-Fi/мобильной сети, авиарежим, недоступная нода, timeout после post.
- [ ] Блокировка экрана и фон во время операции; никаких обещаний непрерывной
      фоновой работы, автоматической подписи или незаметной смены backend.
- [ ] Если появятся профили — раздельные пути, ключи и pending/history;
      переключение во время операции блокируется или безопасно сериализуется.
- [ ] Restore на другом устройстве с независимой сверкой адреса и баланса.
- [ ] Проверить установку native-библиотек, поддерживаемые ABI и размеры страниц
      памяти на целевых устройствах; провести оценку памяти, нагрева и времени scan.

Гейт: матрица с PASS / FAIL / NOT VERIFIED, hash APK/исходников, версия ОС и
модель устройства. Эмуляторные и fault-injection проверки отделены от реальных
сбоев устройства; kill процесса не называется испытанием обрыва питания.

## 8. Этап 5 — testnet-пакет и отдельное решение о mainnet

- [ ] CI: форматирование, статические проверки, Rust/JNI tests, сборка APK,
      инструментальные проверки UI и отдельный управляемый testnet E2E.
- [ ] Секреты CI вне репозитория; тестовые кошельки изолированы от пользовательских.
- [ ] Зафиксированный lockfile, перечень лицензий, SBOM, hashes и соответствующие
      исходники; проверить обязательства Slint только если он попадает в мобильный пакет.
- [ ] Подписанный тестовый пакет, ключ подписи хранится вне репозитория;
      проверить обновление без потери кошелька и документировать правила отката.
- [ ] Инструкция установки, восстановления, известных ограничений и сообщение DEV BUILD.
- [ ] Testnet-приёмка на реальных устройствах; канал распространения и актуальные
      требования магазина проверить отдельно перед публикацией.

Mainnet остаётся закрыт до общего MAINNET_READINESS, независимого аудита и
отдельной приёмки Android. Сам по себе выпуск testnet APK эти гейты не закрывает.
Сроки оценивать после этапа 0, когда подтверждена переносимость зависимостей.

## 9. Учёт прогресса

При начале реализации добавить STATUS.md и WORK_LOG.md рядом с планом. Для
каждого закрытого пункта записывать снимок/commit, команды, итог, артефакт и
границы проверки. Предыдущие 269 desktop-тестов и iOS FFI roundtrip автоматически
не становятся результатами Android. Обновлять статусы только по новым доказательствам.

Следующее действие: этап 0 — зафиксировать базу и доказать сборку общего Rust-слоя
для Android, прежде чем делать полный интерфейс.
